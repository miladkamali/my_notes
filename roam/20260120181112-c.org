** static member of a class
Below is a detailed, practical guide to C++ static class members (both static data members and static member functions) and best practices for initializing them—including the modern C++17+ “inline static” approach and how to avoid the classic static initialization order problems.

1) What is a “static member” of a class?



Inside a class, static means: this member belongs to the class itself, not to any individual object.



There are two main kinds:



A) Static data member (a “class variable”)

Only one instance exists in the whole program, shared by all objects of that class.

It exists even if you never create an object of the class.  



B) Static member function (a “class function”)

Callable without an object: T::f().

Has no this pointer.

Can’t be virtual, const, volatile, or ref-qualified.  

2) Static data members: declaration vs definition (the most important rule)



Key rule



The line inside the class is usually only a declaration, not storage.



cppreference says it clearly: you write static in the class declaration, but you do not write static again in the out-of-class definition.  



Classic (pre-C++17) pattern: declare in header, define in ONE 

.cpp



Header (X.h)

#pragma once

struct X {
    static int n;        // declaration (no storage yet)
};
Source (X.cpp)

#include "X.h"

int X::n = 1;            // definition + initialization (allocates storage)
If you forget the definition, you typically get linker errors like “undefined reference to X::n”.

3) C++17+ best practice: 

inline static

 (define in the header safely)



Why it matters



Before C++17, putting a static data member definition in a header usually caused multiple definitions at link time (because the header is included by multiple .cpp files).



C++17 introduced inline variables, which allow multiple identical definitions across translation units to refer to the same entity (like inline functions).  



Recommended modern pattern

#include <string>

struct X {
    inline static int counter = 0;                // OK in header (C++17+)
    inline static const std::string name{"X"};    // OK in header (C++17+)
};
cppreference explicitly: an inline static data member can be defined in the class definition and does not need an out-of-class definition.  



✅ Use this when:

You’re writing header-only code

You want the simplest correct approach in modern C++

4) Constant static members: 

const

, 

constexpr

, and “ODR-use” pitfalls



A) 

static const int

 (integral/enum) initialized in-class



C++ allows in-class initialization of a const static integral or enum member.  

struct A {
    static const int n = 5;  // OK (integral const)
};
But here’s the pitfall:

Such a member can be “usable for its value” (e.g., array size) but may not be ODR-usable unless you also provide a definition (or make it inline). cppreference’s example labels a non-inline const static as “not ODR-usable”.  



A typical “ODR-use” example is taking its address:

auto p = &A::n; // may require a definition in some standards/contexts
Best practice (C++17+): use 

inline static constexpr



If your intent is “compile-time constant and header-safe”:

struct A {
    inline static constexpr int n = 5; // best practice
};
B) 

static constexpr

 members (since C++11)



cppreference: if it’s constexpr, it must be initialized in-class (no initializer = error).  

struct B {
    constexpr static int arr[] = {1, 2, 3};  // OK
    // constexpr static int k;               // ERROR: needs initializer
};
5) Static member functions: what they can/can’t do

struct IDGen {
    inline static int next = 0;

    static int getNext() {
        return ++next;
    }
};
Notes:

Call it like: IDGen::getNext()

It cannot access non-static members directly (because no this)

It can access static members normally

6) Initialization order: the “static initialization order fiasco”



The problem



If you have non-local static objects across multiple translation units (.cpp files), the order of dynamic initializationacross translation units is not reliably ordered. That can cause one static to use another static before it is initialized.



The safe approaches



Approach A (best general technique): “construct on first use” (function-local static)

Instead of a global/static object, wrap it in a function:

#include <string>

const std::string& configPath() {
    static const std::string path = "/etc/myapp/config.json";
    return path;
}
Function-local statics:

Are initialized the first time execution reaches them.  

Are thread-safe since C++11: if multiple threads race to initialize, it happens exactly once.  



This pattern avoids cross-TU initialization order issues because it initializes on demand.



Approach B (C++20): 

constinit

 to 

force

 static initialization (and fail compilation otherwise)

constinit is designed to prevent “oops, this is dynamically initialized” problems.



cppreference: constinit asserts the variable has static initialization (zero/constant initialization); otherwise the program is ill-formed.  

// C++20
struct C {
    inline static constinit int value = 42; // must be statically initialized
};
If you try to initialize it in a way that requires dynamic initialization, compilation fails (which is good).



Also: constinit does not mean “constant” like constexpr. It doesn’t force const-ness, and it can’t be combined with constexpr.  

7) Best practices summary (practical rules you can apply)



If you can use C++17 or later

Prefer inline static for static data members defined in headers

struct X { inline static int counter = 0; };
This avoids separate .cpp definitions and avoids multiple-definition link errors.  

For constants, prefer:

struct X { inline static constexpr int k = 123; };
Avoid non-trivial “global-ish” initialization across translation units.



Prefer function-local static (construct-on-first-use).  



If you need “must be statically initialized” (C++20):

inline constinit int g = 10;
or inside a class: inline static constinit ...  



If you’re on C++11/C++14

Declare the static member in the class (header).

Define exactly once in a .cpp.

// header
struct X { static int counter; };

// source
int X::counter = 0;
For constants, static constexpr works well, but watch out for ODR-use in older toolchains; when in doubt, give a single definition in a .cpp or upgrade to inline static constexpr in C++17+.  

8) A small “which should I use?” decision guide

Need a shared modifiable value (counter, cache size, stats)?

C++17+: inline static int counter = 0;

Pre-C++17: declare in header + define in one .cpp

Need a compile-time constant (sizes, template params)?

C++17+: inline static constexpr int N = 64;

C++11/14: static constexpr int N = 64; (be careful with ODR-use)

Need to avoid init-order bugs?

Use a function-local static accessor.  

Want the compiler to guarantee no dynamic initialization (C++20)?

Use constinit.
