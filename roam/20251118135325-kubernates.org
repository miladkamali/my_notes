import json, re, subprocess
from concurrent.futures import ThreadPoolExecutor, as_completed

def parse_bytes(val):
    if not val or val == '?':
        return None
    m = re.match(r'^([0-9.]+)(Ki|Mi|Gi|Ti|Pi|Ei)?$', str(val))
    if not m:
        return None
    num = float(m.group(1))
    suffix = m.group(2) or ''
    mult = {'': 1, 'Ki': 1024, 'Mi': 1024**2, 'Gi': 1024**3, 'Ti': 1024**4, 'Pi': 1024**5, 'Ei': 1024**6}
    return num * mult.get(suffix, 1)

def to_gi(val):
    b = parse_bytes(val)
    return '?' if b is None else f"{b / (1024**3):.2f}Gi"

def to_alloc_cap_pct(alloc, cap):
    a, c = parse_bytes(alloc), parse_bytes(cap)
    if a is None or c is None or c == 0:
        return '?'
    return f"{a / c * 100:.1f}%"

def fetch_fs_used_pct(node_name):
    try:
        raw = subprocess.check_output(
            ['kubectl', 'get', '--raw', f'/api/v1/nodes/{node_name}/proxy/stats/summary'],
            stderr=subprocess.DEVNULL, timeout=15)
        fs = json.loads(raw).get('node', {}).get('fs', {})
        used, cap = fs.get('usedBytes'), fs.get('capacityBytes')
        if used is not None and cap:
            return used / cap * 100
    except Exception:
        pass
    return None

Option 1: Check queue timing in logs (works now)
Logs already include queue metrics:

kubectl logs -n prod deploy/haproxy-prod -f
Filter by backend:

kubectl logs -n prod deploy/haproxy-prod -f | grep liveness-detection

Log fields:

Tq — time waiting in the global queue
Tw — time waiting for a free server slot

Example from your cluster:

... liveness-detection liveness-detection_backend/srv1 ... Tq=1 Tw=0 ... Status=200
... face-detection face-detection_backend/srv3 ... Tq=0 Tw=0 ... Status=200
Tq>0 or Tw>0 means the request was queued.

To see only queued requests:

kubectl logs -n prod deploy/haproxy-prod --tail=1000 \
  | grep -E 'liveness-detection|face-detection' \
  | grep -E 'Tq=[1-9]|Tw=[1-9]'

* auto scaling

Your setup today is a fixed-size pool behind HAProxy, with no autoscaling hooks yet. Here is how it works and what you can do.

Current architecture
Clients (sana-core, bff-core, …)
    → haproxy-prod (:7000 liveness, :7500 face)
        → liveness-detection-prod / face-detection-prod (10 pods each, headless svc)
Relevant HAProxy settings:

maxconn 1 per backend pod → each pod handles one request at a time
server-template srv 15 → HAProxy can discover up to 15 pods via DNS
timeout queue 60s → requests wait in HAProxy when all pods are busy
No stats/metrics in the Helm chart today (no queue depth or latency metrics exported)
Both workloads are fixed at replicaCount: 10 with no HPA. The cluster has Victoria Metrics (vm-stack) but no KEDA and no custom-metrics HPA setup for these services.

What you want to scale on

Queue depth and response time are HAProxy-level signals (or app-level if you instrument the gRPC services). Standard CPU-based HPA will not track them well.

Option 1: KEDA + Prometheus (recommended)
Best fit for scaling on queue depth and/or latency with PromQL.

Flow:

Enable HAProxy Prometheus exporter (your legacy haproxy/haproxy-15.cfg already had this on :8404)
Scrape it with VMServiceScrape
Install KEDA
Create ScaledObject per deployment with Prometheus triggers
Example triggers:

# Scale when HAProxy queue > 2 for 2 minutes
- type: prometheus
  metadata:
    serverAddress: http://vmselect.monitoring-system.svc:8481/select/0/prometheus
    query: haproxy_backend_current_queue{backend="liveness-detection_backend"}
    threshold: "2"
# Scale when avg backend response time > 6s
- type: prometheus
  metadata:
    query: rate(haproxy_backend_response_time_average_seconds{backend="liveness-detection_backend"}[2m])
    threshold: "6"
Pros: Native K8s autoscaling, multiple metrics, scales to zero possible, fits your VM stack
Cons: Need HAProxy metrics + KEDA install + tuning to avoid flapping

Option 2: HPA v2 with custom/external metrics
Same metrics as Option 1, but via prometheus-adapter (or Victoria Metrics custom-metrics bridge) feeding the Kubernetes metrics API.

metrics:
  - type: External
    external:
      metric:
        name: haproxy_backend_current_queue
        selector:
          matchLabels:
            backend: liveness-detection_backend
      target:
        type: AverageValue
        averageValue: "1"   # scale when >1 queued request per “unit”
Pros: No KEDA; built-in HPA
Cons: Harder to combine multiple signals; you need a metrics adapter; less flexible than KEDA

Option 3: App-level metrics + HPA/KEDA
Instrument liveness/face-matching to expose:

grpc_server_handled_total
grpc_server_handling_seconds (histogram → p95 latency)
active / in-flight requests
Then scale on:

sum(grpc_server_handling_seconds_sum) / sum(grpc_server_handling_seconds_count) > 5
# or
sum(grpc_server_started_total - grpc_server_handled_total) > N
Pros: Measures actual service performance, not just proxy queue
Cons: Requires app changes; queue at HAProxy can still build if HAProxy maxconn is the bottleneck

Option 4: CPU/memory HPA (quick but weak)
Add HPA like ha-web has, targeting CPU or memory.

Pros: Simple, no new infra
Cons: Your pods request 100m CPU but limit 3000m; inference may not show high CPU until already saturated. Does not scale on queue or latency.

Option 5: Custom autoscaler controller
A small controller (CronJob or Deployment) that:

Queries HAProxy stats socket (show stat)
Computes desiredReplicas = ceil((current_sessions + queue) / target_per_pod)
Patches the Deployment
Pros: Full control, no KEDA
Cons: You own reliability, cooldowns, and edge cases

Option 6: Scale HAProxy itself (usually not enough)
Scaling haproxy-prod helps only with HAProxy CPU/network. It does not add inference capacity. You need to scale liveness-detection-prod and face-detection-prod.

Practical recommendation
For your exact goals (queue + avg response time), a sensible path is:

Phase 1 — Observability (required for any good autoscaling)
Add to helm-charts/apps/haproxy/templates/configmap.yaml:
stats socket (admin API)
Prometheus exporter frontend on :8404 (as in legacy config)
Add VMServiceScrape for haproxy-prod
Confirm metrics like:
haproxy_backend_current_queue
haproxy_backend_http_total_time_average_seconds (or equivalent)
haproxy_backend_current_sessions
Phase 2 — Autoscaling
Install KEDA in the cluster
Add ScaledObject to liveness-detection and face-detection charts
Start with queue depth as primary trigger (directly matches your goal)
Add response time as secondary trigger or use KEDA advanced scaling with multiple triggers
Phase 3 — Tune

Scaling formula (intuition)
With maxconn 1 per pod:

needed_replicas ≈ ceil((active_requests + queue_depth) / 1)
Using latency (Little’s Law):

needed_replicas ≈ ceil(arrival_rate × avg_response_time_seconds)
Example: 2 req/s × 5s avg response → ~10 replicas (matches your current fixed size).

set -euo pipefail
DOMAIN="${RENEWED_LINEAGE##*/}"   # e.g. uid.ir or u-id.net
LIVE_DIR="/etc/letsencrypt/live/${DOMAIN}"
CRT="${LIVE_DIR}/fullchain.pem"
KEY="${LIVE_DIR}/privkey.pem"
# --- 1) HAProxy edge (both domains) ---
HAPROXY_CERT_DIR="/usr/local/etc/certs"
install -m 644 "${CRT}" "${HAPROXY_CERT_DIR}/${DOMAIN}.pem"
cat "${KEY}" >> "${HAPROXY_CERT_DIR}/${DOMAIN}.pem"
# If HAProxy uses a combined PEM per domain, adjust naming to match your layout
systemctl reload haproxy || service haproxy reload
# --- 2) Kubernetes secrets ---
case "${DOMAIN}" in
  uid.ir)
    kubectl -n production create secret tls wildcard-uid-ir-tls \
      --cert="${CRT}" --key="${KEY}" \
      --dry-run=client -o yaml | kubectl apply -f -
    kubectl -n production create secret tls uid-ir-tls-secret \
      --cert="${CRT}" --key="${KEY}" \
      --dry-run=client -o yaml | kubectl apply -f -
  ;;
  u-id.net)
    kubectl -n production create secret tls wildcard-u-id-net-tls \
      --cert="${CRT}" --key="${KEY}" \
      --dry-run=client -o yaml | kubectl apply -f -
  ;;
esac  


Register it with certbot:




sudo chmod +x /usr/local/bin/cert-deploy.sh
# Run once after initial issuance
sudo certbot renew --cert-name uid.ir --deploy-hook /usr/local/bin/cert-deploy.sh
sudo certbot renew --cert-name u-id.net --deploy-hook /usr/local/bin/cert-deploy.sh

Certbot usually installs a systemd timer. Verify:

sudo systemctl status certbot.timer
